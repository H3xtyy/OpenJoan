# The 64-bit design

How OpenJoan, whose code mirrors a 32-bit program function by function, runs on x86-64 (Linux and Windows). State
of 2026-11-08, after the Phase 2 exit. Other pages: `ARCHITECTURE.md` (the runtime model), `RUNTIME.md` (start-up,
settings), `X64_STATE_CHECK.md` (the parity check).

Some source comments cite design notes (`claude/X64.md` and others) that are lost. This page
describes the code as it is; it is not a reconstruction of them.

## 1. What differs between the two layouts

The original is a 32-bit program, so everything the game stores in memory has x86 widths: a pointer is 4 bytes, a
code address is 4 bytes, `long` is 4 bytes, and structs lay their pointers out at 4-byte steps. OpenJoan keeps the
x86 numbers where the *game* defines them and uses native widths everywhere else.

| Thing | x86 (reference build) | x64 |
|---|---|---|
| pointer, `uintptr_t`, `size_t` | 4 bytes | 8 bytes |
| a stored pointer of the data image (`uptr`, `src/data/data_common.hpp`) | 4 bytes | 8 bytes |
| size of `joan_image` | 0xa1000 bytes (`img::kSize`) | 0xa8a6c bytes, 7,835 pointer slots widened (`src/data/image_xlate.inc`) |
| game classes (`src/original/gen/*_fields.inc`) | pointer members `void*` at their original offsets, `static_assert(offsetof)` | the same members, 8 bytes each, so every later offset moves; the `// 0x..` comments are x86 offsets |
| vtable entry | 4 bytes | 8 bytes; index a `void**` by slot number, never add a byte offset (`call::vtable_of`, `x86_vslot`: `src/call.hpp`) |
| code address in a vtable / callback / saved record | the original code address | a pointer to our function (the code slot's target); a saved one is written as its original address (section 5) |
| calling conventions | `__thiscall` / `__stdcall` / `__cdecl` distinct on MSVC | one convention per platform; `call.hpp`'s `thiscall<R>`, `cdecl_call<R>` ... all collapse (section 6) |
| floating point | x87, 53-bit mantissa / 24-bit precision control as the game set it | emulated bit-exactly on SSE2 in `src/fp/` on both widths; x64 runs as 24-bit precision with round-to-nearest (`fp/precision.hpp` `current_precision`) |
| save-file bytes | 4-byte pointers | the same bytes: saves are written field by field (section 5) |

Rule of the port: a value that is a pointer, a size or an address is pointer-sized in OpenJoan; a value the *game*
stores as 32 bits (a field, a file record, a hash) stays 32 bits. The two named narrowings, `register_low_bits` and
`pointer_low_dword` (`src/call.hpp`), exist for the few places where the low 32 bits of a pointer are exactly what
the original kept (a register left at an address, an emulated stack-frame dword, one unread image slot).

`#pragma pack(1)` is on the generated layouts on both widths; the offset asserts are compiled on x86 only
(`UINTPTR_MAX == 0xffffffff`), because on x64 the offsets legitimately differ.

## 2. The data image on x64

The original's `.rdata/.data/.bss/.idata` is the one object `joan_image` (`docs/RUNTIME.md` section 2). Its typed
layout `src/data/layout.hpp` declares every stored pointer as `uptr`, so the compiler lays the object out with
8-byte pointers on x64.

- **Map.** `src/data/image_xlate.inc` is the piecewise-linear map "original address -> offset in the x64 object":
  `JOAN_IMAGE_X64_SIZE(0xa8a6c)` and 7,836 `JOAN_XLATE(va, off)` runs; a run says "addresses from `va` on, up to the
  next run, are at `off + (address - va)`". An address inside a pointer maps to the low half of the 8-byte slot.
- **Generator.** `re/image/gen_xlate.py` asks the compiler (libclang, `re/image/probe.py`, over `layout.hpp` for i686
  and x86_64), pairs the pointer leaves of both layouts, writes the file and checks that both layouts have the same
  leaves in the same order, that the bytes between two pointers have the same size, and that every word of
  `data_relocs.inc` is a pointer leaf. Rerun it whenever `layout.hpp` changes (the generator of `layout.hpp` is
  `re/gen_data_curated.py`); the file is generated, never edited.
- **Consumers.** `img::offset_of(va)` and `img::original_of(off)` (`src/runtime/image.hpp`) are `constexpr` over the
  runs, so `d::` names resolve at compile time; `data_image::relocate` writes relocated pointers as `uintptr_t` at
  `offset_of(site)`; the replay's x86 view (section 8) uses the same file.
- **Reading a slot.** A 4-byte slot stays `u32`; a widened slot is a pointer and is read as one. `img::global<T>(d::X)`
  uses the type the layout gives. The loader fills `.idata` as an array of 8-byte slots (`resolve_imports`,
  `ImportFn::slot` is `std::uintptr_t*`).
- **Code pointers.** The image's 1,568 code pointers are set to the target of their code slot after the code table is
  sealed (`relocate_code_pointers`, `docs/RUNTIME.md` section 1); on x64 a trap stub is 24 bytes of x64 code
  (`src/runtime/code_slots_core.hpp`, `kTrapStubSize`: `mov ecx, slot; mov rdx, [rsp]; mov rax, handler; jmp rax`) because a call to a handler more than 2 GB away does not fit a
  `call rel32`.
- **Two build facts.** The stray guard and `image_runtime.hpp kOldLow/kOldHigh` still name the original's address
  range 0x00400000..0x00a96000 and report a fault there; on x64 that range can be mapped by anything, so raw
  old-range values are told apart by what is mapped (`docs/RUNTIME.md` section 2).

## 3. Typed layouts, the main source of x64 bugs

`src/original/gen/` (generated from `re/layout/layouts.json` by `re/layout/gen_types.py`, facades by
`re/facades/gen2.py`) gives each game class its fields. Code that reads the object through the class is width-correct
on both builds. Code that reads it at a raw x86 offset (`at<T>(p, 0x1c)`, `p + 0x50`, `p[0x124]`) is correct on x86 and
reads the wrong bytes on x64 as soon as a pointer precedes the field. The port removed those reads from the game code;
the hazard meter (section 7) keeps count. The bug classes that surfaced in the owner's x64 runs, with the tools that
now find them (all `tools/x64_scan_*.py`, run from the repository root):

| Class | Example | Scanner |
|---|---|---|
| x86-sized byte shell for an object that holds pointers (`struct S { u8 b[0x1a0]; }`) | the `FileTxt` shell overran the frame; fix: `sizeof(jo::Class)` | `x64_scan_shells.py <x64 binary> <x86 binary>` (sizes from DWARF) |
| partial "view" layout applied to an object of another class: same offset on x86, different on x64 | `Point::inside` read the mouse position at an `Input` x86 offset; `D3D` view on `SysEn` | `x64_scan_view_classes.py`, `x64_scan_two_layouts.py` (advisory), `tools/x64_view_classes/` |
| raw offsets on byte pointers | `p[0x124]`, `o[0x50]` | `x64_scan_raw_index.py`, `x64_raw_offsets.py` |
| a pointer cut to 32 bits at a call (`arg::u32(p)`) | `Unit::set_group` took a `World*` as `int32_t`: fine while the heap was below 4 GB, a crash once it moved above | `x64_scan_ptr_as_u32.py`, `x64_scan_u32_to_ptr.py`, `x64_scan_facade_returns.py` |
| an output argument that is a 4-byte local while the callee stores a pointer through it | `Actor::draw` lost every static plane | `x64_scan_out_params.py` |
| by-value structs and float / integer kind mismatches across a facade | section 6 | `x64_scan_byvalue.py`, `x64_scan_abi_kinds.py`, `x64_scan_raw_calls.py` |

Findings of the audits are in `re/x64_census/reports/` and `re/x64_census/sweep-2026-10-31/`.

Missing or wrong fields are fixed in the layout spec (`re/layout/spec`), the generated files regenerated, and the
code changed to use the member; generated files are never edited by hand.

## 4. Where memory lives: no address-space crutches

During the port the 64-bit builds were kept below 2 GB so that a pointer stored in a `u32` survived. That hid the
bugs of the "pointer cut to 32 bits" class and is gone:

| Platform | Was | Now |
|---|---|---|
| Windows x64 | `/LARGEADDRESSAWARE:NO /HIGHENTROPYVA:NO /BASE:0x10000000` (MinGW: `-largeaddressaware:no`, `--disable-high-entropy-va`, `--image-base`) | `/DYNAMICBASE /NXCOMPAT /LARGEADDRESSAWARE /HIGHENTROPYVA`, default base (`src/CMakeLists.txt`); the `JOAN_LARGE_ADDRESS_AWARE` option was deleted with the Win32 presets |
| Linux x64 | planned non-PIE / low allocations | PIE (the distribution default); `-no-pie` and `-fno-pie` are applied only when `CMAKE_SIZEOF_VOID_P` is 4 |
| Linux x86 | fixed-address executable (`-no-pie`) | unchanged: it is the objcmp reference (`tools/objcmp-x86.sh`) and replays x86 recordings; a PIE keeps the GOT address in `ebx` and would change the code |

The data image, `joan_code[]` and the
heaps therefore lie above 4 GB on x64. In recordings the **deterministic heap** is also above 4 GB: the arena is
reserved at `0x7e00'0000'0000 + {0x20000000, 0x30000000, 0x40000000, 0x50000000}` (the first free one), keeping the low
32 bits the x86 bases have, which is all a recording keeps of a heap address (`src/runtime/det_heap.cpp`
`init()`). This is deliberate: a replay on x64 would otherwise never show a pointer truncated to 32 bits, which
is how `Unit::set_group` passed every replay and crashed live (2026-10-30).

Other points of the x64 runtime that are by design:
`joan_code[]` is `uintptr_t`; `JOAN_REPLACE`, `redirect_function` and `patch_import` carry `uintptr_t`; import
overrides and dead-import traps are plain function pointers; `fp/` is portable SSE2; there is no inline assembly and
no SEH frame; the crash handler and the stray guard read the native context.

## 5. Field-wise saves

A raw `file_write(record, sizeof)` would write x64 object bytes, which no build reads. All save records are therefore
serialised field by field into exactly the bytes the 32-bit `joan.exe` wrote, on both widths: an original `.SAV` loads
on x64 and a save written on x64 loads on x86 (`src/save/README.md`).

- `src/save/io.hpp`: `Out` collects the bytes of one original `File::file_write(p, n)` call field by field and hands
  them over in one call; `In` reads one chunk with one `file_read`, so the game's size-tolerant "vary size" reading is
  unchanged. Little-endian, floats as bit patterns.
- Pointer fields carry a policy (`Ptr`): `Flag` (the reader only tests it for null, then re-creates the object), `Cleared`,
  `Kept` (x64: `In` leaves the field alone), `Image` (an address of the data image or of code: written as the
  *original* address, relocated back on load: `img::save_words` / `load_words`), `Stale`. On x64 a `Flag` pointer is
  written as a token that is 0 exactly when the pointer is null (low 32 bits | 1 otherwise); data pointers are
  re-created on load, never stored.
- `src/save/gen/records_s0.hpp` .. `records_s6.hpp` are generated by `re/save/gen_save.py` from `re/save/records.json`
  (a libclang pass over the layouts, which needs the llvm-mingw sysroot `JOAN_MINGW`); `records_s3.hpp`,
  `records_s4.hpp`, `s5.hpp` are hand-written chunks the generator cannot express.
- Settings: `[Debug] SaveFieldwise` (default 1; on x64 always on), `SaveCompare` (x86 only: each chunk compared with the
  raw bytes), `SaveAudit` (finding image / heap values in written data); `docs/RUNTIME.md` section 3.9.
- Verification: `re/save/test` (serialiser on real structs, i686 and x86_64, golden file), `re/save/savecmp.py`
  (compares two save folders), the replay recordings (saves are part of the environment fingerprint).

## 6. Calls across the facades: the by-value and register-kind ABI

The generated facades (`src/original/gen/*_methods.inc`) and the call helpers (`src/call.hpp`: `thiscall<R>`,
`cdecl_call<R>`, `stdcall_call<R>`, `import_call<R>`) call original addresses, which are slots leading to our C++
replacements. On x86 every argument is a dword on the stack, so a float passed as dword bits or an integer passed as a
float works. On x64 the registers differ by kind: a `float` argument travels in an XMM register and an integer or
pointer in a general register (System V on Linux; the Microsoft x64 convention likewise assigns by position and kind),
and a struct larger than a register is passed by reference or by classification of its members. Caller and callee must
therefore agree on the **kind** of every argument and result, not just its size. Cases found and fixed:

- `Vec3` of three `u32` passed to a callee taking three floats (13 sites; `Box::face_hit` 0x0069ea70 to
  `box_outside_region` 0x0069a300, the pick ray to `Shape::sphere_hit` ..., `Fog::set_range` 0x005c0a70): the callee read
  integer registers and got garbage that depended on earlier calls. Floats are carried as float members or as
  dword bits in an explicit struct; `joan::orig::arg::*` adapters make the x86 calling sequence explicit.
- float angles passed to setters that take the dword of the angle: on x64 the float went to XMM and the setter read an
  integer register (`EffectState::update_parts`; the first bug the state check found, `X64_STATE_CHECK.md`).
- results and out-parameters: a facade returning `u32` for a replacement that returns a pointer truncates it; a 4-byte
  local given to a callee that stores 8 bytes clobbers its neighbour.
- varargs (`printf` family) read 8-byte slots on x64; callee-side types must match.

Rules for new code: a facade, a replacement and every call site agree on pointer vs 32-bit integer vs float for each
parameter; structs passed by value have the callee's member kinds; run the scanners of section 3 after touching
facades. The generated facade declarations come from `re/facades`; a wrong type there is a request to the generator,
not an edit of `gen/`.

## 7. The hazard meter

`python3 tools/x64_hazards.py [--by-file] [--baseline re/x64_census/hazards_baseline.txt]` counts, per directory of
`src/` (generated `src/data` excluded), the textual patterns that are 32-bit assumptions the compiler does not
report. Counts are regular-expression matches in `.cpp/.hpp/.inc/.h` files, a trend and not a proof.

| Column | Counts | Target |
|---|---|---|
| `raw_ptr` | `at<T*>(p, off)`: 8 bytes read at an x86 offset | 0 |
| `raw_u32` | `at<u32>(p, off)`: may hold a pointer | 0 |
| `raw_any` | every raw field access `at<T>(p, off)` | only in files with a documented reason (143 today) |
| `vtbl4` | vtable reads assuming 4-byte entries (`void***`, `off / 4]`) | 0 |
| `slot_call` | calls of original addresses through `thiscall<` / `cdecl_call<` ... / `vcall<` | information |
| `orig_fwd` | facade forwards `orig::name(` | information |
| `img_use` | data-image symbols `d::name` used | information |
| `ptr_u32` | `static_cast<u32>(reinterpret_cast<uintptr_t>(...))`: a pointer in a `u32` | 0 |
| `naked`, `asm` | `__declspec(naked)`, `__asm` | 0 |
| `x87emu` | `x87::Fpu` / `x87::ftol` uses | information |
| `raw_add` | a field reached as `pointer + constant` (`add(this, N)`, `self() + N`) | down only; `tools/x64_raw_offsets.py` lists the sites |
| `narrow64` | a code address or pointer-sized integer cut to 32 bits through `arg::u32` / `arg::i32` / `static_cast<i32>` | down only |

Phase 2 exit: `raw_ptr`, `raw_u32`, `ptr_u32`, `vtbl4`, `asm`, `naked` at 0. Totals on 2026-11-08 (`TOTAL` line):
`raw_ptr 0, raw_u32 0, raw_any 143, vtbl4 0, slot_call 1740, orig_fwd 27988, img_use 21336, ptr_u32 0, naked 0, asm 0,
x87emu 761, raw_add 399, narrow64 8`. The committed baseline `re/x64_census/hazards_baseline.txt` differs by
`slot_call +3`, `orig_fwd -68`, `img_use -28`, `x87emu +12` (the information columns move with the code; the
baseline is updated only downwards for the target columns). The meter counts `p + 0x..` arithmetic only roughly and does
not see `bp(...)` frame views: grep for them too.

The compiler is the second meter: x64 builds are `-Werror` with `-Wall -Wextra -Wpedantic -Wshadow -Wconversion`
(`JOAN_WARNINGS_AS_ERRORS`; `CMakeLists.txt`), which catches pointer-to-integer and 64-to-32 truncations;
`re/x64_census/` keeps the earlier census.

## 8. Replay across widths

A recording keeps, per frame, a hash of the normalised `.data`/`.bss` of the image. The hash is defined in the **x86
layout**, so one recording serves both builds:

- **The x86 view.** On x64 `src/runtime/replay/x86_view.hpp` copies the hashed range into an x86-layout buffer: every
  original byte is read from the x64 location of its field (the run of `image_xlate.inc`), and a widened pointer
  contributes its low 4 bytes. The typed hash table `hash_types.inc` (generated by `re/replay/gen_hash_types.py` from
  `layout.hpp`, in x86 offsets) then applies unchanged. `hash_types_check.cpp` checks the table against the compiler's
  x64 layout; `re/replay/test_x86_view.cpp` and `check_x64_view.sh` test the mapping. The same file provides the inverse
  mapping for an x64 recording replayed by any build (`replay.cpp normalise_in`).
- **`normalise_wide`** (`replay.cpp`, x64 only). The low half of a widened pointer cannot be classified: with PIE, ASLR
  and the heap above 4 GB it falls into the 32-bit range of the heap, image or code stubs by chance, differently each
  run. So every widened pointer is normalised from its **full** value: window -> `kTagWindow`; small handle ->
  `kTagHandle`; inside the deterministic heap -> `kTagHeap | offset`; inside the image -> its original address
  (`img::original_of`); inside the executable -> `kTagPointer`; a code-slot trap stub -> the original code address; any
  other pointer -> `kTagPointer`. 4-byte image slots that hold the low half of a pointer and that nothing reads
  (`g_surface_base`, 0x00a15010) are not hashed on x64.
- **The recorded hash cannot match on x64**: it covers values that legitimately differ, such as the element
  sizes of pointer lists, heap offsets and the renderer's ring-buffer bookkeeping (which depends on the stream cache,
  keyed by address). The x64 replay's own hash comparison is therefore information only
  (`ReplayHashSkipReplay` can mask the width-dependent words to reach the real differences).
- **The state check** replaces it. `tools/x64_state_check.sh <recording> [every] [--x64-recording]` replays the recording
  on an x86 and on an x64 copy with `ReplayDumpImage`, and `tools/replay_image_diff.py` compares the typed
  non-pointer words, leaving out pointers, untyped bytes and the words of `re/replay/x64_layout_words.txt` (each with
  its measured reason). The x86 replay must match the recording frame for frame, which ties the comparison to the
  recorded game. Procedure, coverage by mission and the findings: `X64_STATE_CHECK.md`. Phase 2 exit criterion: every x86
  reference recording replays on x64 to its end and the state check finds no difference.
- **What the check does not see:** pointers and untyped bytes (a wrong pointer shows as a crash, which the high
  deterministic heap provokes), and how many draws a frame made (a missing model shows in the smoke checklist).

## 9. Windows x64

MSVC builds (`windows-hook-x64`, `vs2026-hook-x64`, `vs2026-hook-x64-release`) are for CI and Visual Studio users; while
the repository is private, GitHub Actions is not available and Windows x64 is cross-built on Linux with llvm-mingw
(preset `mingw-x64`, `cmake/llvm-mingw-x64.cmake`: llvm-mingw 20240619, clang 18). The cross build does not
run the game and does not show MSVC-only diagnostics. It needed three portability fixes (the POSIX shims of
`compiler.hpp` under MinGW, `<cpuid.h>` versus `<intrin.h>`, `crash.cpp`'s `_ReturnAddress`: `JOAN_RETURN_ADDRESS()`).
The build handles Itanium-ABI member pointers (`src/runtime/patch.hpp`, `src/call.hpp`), as the Linux builds do, and it
has not been run on Windows yet.
