# Attribution of the reimplemented functions to the original source files

Generated by `re/attribute.py` (rerun: `python3 re/attribute.py` from the repository root; inputs: the reference build's disassembly and function lists, the `src/**` registrations and `re/functions.csv`; the counts below are a snapshot of the first run). Per-function result: `re/attribution.csv`.

## Method

* **anchor** - the function references a `d:\ww\...\x.cpp` `__FILE__` string (119 distinct in .rdata, 118 .cpp + `stackt.h`), or a manual attribution in `re/functions.csv`, or (libraries) its name identifies the VC6 CRT / IJG libjpeg / D3DX8 source.
* **link order** - the `__FILE__` strings sit in .rdata in project order (ww/ alphabetical, then ilib/, elib/, en3d/, en2d/, uti3d/, interfac/). That order is the object order of .text too, so the code is segmented with a forward-only Viterbi pass over the functions in address order (anchors weigh 10, private .rdata / initialised .data references 1 each, a new object costs 3).
* **range** - the function lies between two in-place evidence functions (anchor, or private .rdata/.data references inside the file's data extent learned from anchored code) of the same file, or it has such private data references itself.
* **class** - at a segment edge: the class name of the registration (classes whose evidence-backed functions are >= 75 % in one file) or call-graph neighbours pick one of the two neighbouring files; also the manual `functions.csv` attributions.
* **guess** - at a segment edge with no own evidence: the nearer of the two neighbouring files (<= 12 functions from evidence).
* **unknown** - more than 12 functions away from any in-place evidence: most of these stretches are objects without a `__FILE__` string (see the list below); they are not forced into a neighbour.
* Functions whose own `__FILE__` / private data contradict their code position (incremental-link moves: the exe was linked with /INCREMENTAL, functions that grew were moved into holes) keep their own file; the evidence says "code outside its object range".

### Findings

* joan.exe is an **/INCREMENTAL** link: thunk table at 0x401000, functions padded and moved into holes when they
  grew. Out-of-order `__FILE__` users (e.g. `WorldS::add_entry` 0x42b270 with `world_s.cpp` in the middle of
  the camres..cpuusage area; `ilib/sound3d.cpp`, `se.cpp`, `mousecr.cpp` users at 0x48d120..0x4941b0 among the
  root `i*` files; `unitlvl.cpp` at 0x4a95a0) are moved functions; three game functions even sit after the CRT
  (0x7c6240, 0x7c7ab0, ...). Position-only attributions (`range`, `guess`) can therefore be wrong for single
  moved functions that have no own evidence.
* Link order = .rdata `__FILE__` order: root `ww/` alphabetical, then `ilib/`, `elib/`, `en3d/`, `en2d/`,
  `uti3d/`, `interfac/` (project groups, alphabetical inside).
* Only 413 of ~9,600 game functions reference a `__FILE__` string and only ~1,800 have private data
  references, so most objects are known by 2-15 anchors. Many objects have **no `__FILE__` string at all**
  (they never call the allocator / error reporter with `__FILE__`); the largest unattributed stretches are
  real objects: 0x561270..0x577720 (1,109 registrations, `Pixel`/`Blit`/`StaticInit`) between `world_s.cpp`
  and `ilib/audio.cpp`, 0x4d30f0..0x4de7e0 (404, the `Menu`/`OptMenu`/`ObjMenu` handlers) between
  `speech_s.cpp` and `t_scrres.cpp`, 0x649860..0x661ea0 (445, `Script`) between `uti3d/esstate2.cpp` and
  `uti3d/lflare.cpp`, 0x42ced0..0x43ca90 (203, `Unit`/`Order`/`Player`) between `camres.cpp` and
  `cpuusage.cpp`.
* Game code ends at **0x763d00**, not 0x7693c4 (re/make_csv.py `region()`): import jump stubs 0x763d02..,
  D3DX8 texture loaders + its libjpeg error manager from 0x763fc0, D3DX math 0x7669fb... `functions.csv`
  labels 0x763d00..0x7693c4 as `game`.
* `.bss` is not in object order (communal variables), so only `.rdata` and initialised `.data` references
  are used as evidence.
* `src/data_names.hpp` has 107 of the 119 `__FILE__` strings as `s_d_ww_*`; gamefil2, gamefile, unit,
  ilib/dynarr, dynarrb, filemem, filetxt, gameset, resdb, reslx, resx and en3d/texturea are named otherwise.

## Layout

One `.cpp` per original source file, with the same base name, under `src/` (`src/ilib`, `src/elib`, `src/en2d`, `src/en3d`,
`src/uti3d`, `src/interfac`, `src/game` for the `d:\ww\*.cpp` root files, `src/lib/crt`, `src/lib/d3dx8`, `src/lib/jpeg`,
`src/lib/openal`, `src/lib/imports`). Stretches with no evidence live in `src/game/unknown_<class>.cpp`. The per-function
mapping is `re/attribution.csv`; per-file counts are in `re/attribution_summary.md`. 

Registration names (`JOAN_REPLACE*("module", ...)`) appear in the logs; the registry key is the address.
