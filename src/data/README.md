# `src/data/`: the data image as committed typed source

The original executable's static data (`.rdata`, `.data`), its `.bss` and `.idata` are one object of OpenJoan,
`joan_image`, laid out exactly as the original laid them out from address 0x009cf000 (`img::kVa`) to 0x00a70000.
Everything in this folder is **generated** by `re/gen_data_curated.py` from the reference build of `joan.exe`
(6,680,784 bytes, PE timestamp 0x400BA40A) and from the readers in `src/**`; nothing here is edited by hand. The
decision to commit the values as typed C++ rather than read them from the player's executable is
`src/data/README.md`.

OpenJoan never reads `joan.exe`: neither at build time (the extraction path was deleted in Phase 1)
nor at run time. The data files of the game (`Resource/`, `map/`, `unit/`, ...) are the only input.

## Files

| File | Size | Content |
|---|---|---|
| `layout.hpp` | 1.25 MB | the **layout**: one packed struct per chunk of `.rdata` / `.data` (91 chunks, 10,564 members at their original offsets, each with `// 0x<addr> \| <kind> \| used by <files>`), `struct Bss` from `bss.inc`, and `struct Image` (chunks at their offsets, zero gaps for dead objects and padding, `.bss`, `.idata`). No values |
| `rdata.inc`, `data.inc` | 1.5 MB, 0.8 MB | the **values**: the same chunk structs with their members' initialisers (strings, tables, floats, vtables as `JOAN_CODE_PTR(addr)`, data pointers as `JOAN_DATA_PTR(addr)`). Included by `image.cpp` only |
| `image.cpp` | 12 KB | the one `constinit` object `joan_image_typed` (= `extern "C" joan_image`, `src/runtime/image.hpp`): `struct Image` with the values. Constant-initialised by the compiler, so no constructor runs before the relocation |
| `bss.inc`, `bss_classes.hpp` | 100 KB, 7 KB | `.bss` as typed members (the game's global objects with their classes from `src/original/`, pointers as pointers; unreviewed symbols as bytes) and the class headers it needs. Zero: no initial values |
| `dead.cpp` | 73 KB | `kDeadRanges`: the 1,130 ranges (1,794 objects, 55,832 bytes) left out of the image because nothing reads them (C++ exception tables of the original frames, data read only by the replaced CRT / D3DX / libjpeg code), with the reason per range; `kSections`: per section its range, typed bytes and dead bytes |
| `data_relocs.inc` | 150 KB | `JOAN_DATA_RELOC(address, kind, value)` for every stored pointer of the emitted image (2,338): 770 data pointers (an address inside the image) and 1,568 code pointers (an original code address: vtable entries, CRT initialisers, callbacks) |
| `data_symbols.inc` | 350 KB | `JOAN_DATA_SYMBOL(section, type, name, address)` for every live object (5,806, `.bss` included): the names of `src/data_names.hpp` (`d::g_units`), the reference test's section check |
| `data_common.hpp` | 2 KB | element types (`u8` .. `u64`, `Guid`, `uptr` = a stored pointer: 4 bytes on x86, 8 on x64), the `JOAN_*_PTR` macros, the `DeadRange` / `Section` tables' declarations |
| `image_xlate.inc` | 251 KB | **x64 only**: stored pointers widen to 8 bytes, so the x64 object is the compiler's layout of `layout.hpp` (0xa8a6c bytes instead of 0xa1000; 7,835 slots widened) and an original address maps to its offset through these runs (`JOAN_XLATE(va, off)`), constant-evaluated for the `d::` names. Generated by `re/image/gen_xlate.py` from both layouts |
| `image_xlate_probe.inc` | 1 KB | the identity stand-in `gen_xlate.py` compiles with while it asks the compiler for the x64 layout; never part of a build |

The values are a typed transcription of about 350 KB of the executable's static data: 600 initialised globals,
3,854 strings, 94 blobs, 176 pointer tables, about 430 numeric constants, 143 zero-initialised objects. They
contain no asset and no player-facing text (those are in the game's data files); the asset lint
`tools/check_no_assets.py` checks every commit against the game folder.

## How the image is used

- **Start-up** (`src/runtime/image_runtime.cpp`, a compiler-segment static initialiser that runs before any other static
  constructor of ours): `data_image::check_sections()` checks that every dead range lies in its section, then
  `data_image::relocate(joan_image, img::base())` moves the 770 data pointers from their original values to
  where the object really is. Code pointers keep their original addresses until the code table is sealed; then
  `relocate_code()` points them at their slots' targets (`loader/joan_re.cpp`), `.rdata` is made read-only, and
  the game starts. `[Loader] PoisonDead=1` fills the dead ranges with 0xCD for a run that proves nothing reads them.
- **Access** (`src/runtime/image.hpp`, names in `src/data_names.hpp`): `img::ref(d::flt_x)`, `img::obj(d::g_units)`,
  `hook::global<T>(d::g_x)`, `img::str(d::s_...)`, `img::offset_of(va)`. An original address is an `img::Addr`,
  never a plain integer; a value computed at run time goes through the raw overloads, which log a `stray image
  address` when it is an unrelocated original address.
- **Saves** (`image.hpp save_words / load_words`): a dword that points into the image is written to disk as its
  original address and relocated back on load (x86 layout; Phase 2 makes the save records field-wise).
- **Replay** (`src/runtime/replay/`): the per-frame state hash covers `.data` / `.bss` of this object through the typed
  table `src/runtime/replay/hash_types.inc`, generated from `layout.hpp`.

## Verification

`tests/data_image_reference_test` (target `data_image_reference_test` of every game build, run by `ctest`):
every symbol fits its section, every pointer word holds its original value, relocation of copies at 32 / 35
bases and of the real object in place; and, when `$JOAN_GAME_DIR/joan.exe` is the reference build (SHA-256
`ad1dd30f...`), every byte of the committed `.rdata` / `.data` equals the executable's byte at the same original
address (pointer slots through their original value, dead ranges zero, x64 slots through `image_xlate.inc`).
Without the executable the test exits 77 and CTest reports it `Skipped`. A regeneration or a rename of a member is
correct when this test passes and the reference replay is identical.

## Regenerating

```sh
# the inputs (`docs/re/BINARY.md`): a re/ folder BESIDE the checkout with the reference joan.exe and its
# objdump listing, and the function / thunk databases re/analyze.py makes from them (git-ignored)
python3 re/gen_data_curated.py ../re/joan.exe ../re/joan.asm functions.json thunks.json src
python3 re/image/gen_xlate.py --data src/data -o src/data/image_xlate.inc   # after any change of layout.hpp
python3 re/gen_data_names.py ../re/joan.exe src src/data_names.hpp
```

`.data` and `.bss` are pinned: the replay hashes them with the types of the layout the recordings were made with,
so the generator copies their members, names, types and chunks from the committed `data.inc`, `bss.inc`, `layout.hpp`
and `data_symbols.inc`, and refreshes only the `used by` lists. An object in `.data` can be dead only inside the
ranges of `re/replay/frozen_data_dead.txt`; if the emitted or dead byte counts change, the generator stops. Only
`.rdata` is derived anew.

`--check` with the same arguments exits 1 when the committed files differ from what the current `src/**` gives:
an object nobody named when the files were generated may have been left out (zero in the image), so regenerate
after a change that names a new data address. Renames of `d::` names go through the generators' naming tables
(`re/rewrite_data_names.py` over the committed files is the fallback; the next regeneration must reproduce the
same text).

## Rules

- Generated: do not edit. A wanted change goes into the generator or its spec and is regenerated.
- No new untyped `u8` blobs: every added member has a type, a name and a reader (`docs/CONTRIBUTING.md` section 5).
- The image holds no asset, no bitmap, no sound, no text table and nothing copied byte for byte from a game file.
- On x64 a 4-byte slot stays `u32`; a widened slot is a pointer and is read as one. Offsets are computed, never
  written as `0x...` constants.
